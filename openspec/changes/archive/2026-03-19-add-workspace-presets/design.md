## Context

`kickstart` 当前只有一条主流程：扫描最近活跃的 Git 仓库、让用户多选项目、然后在 iTerm2 中统一打开。现有程序已经把轻量级本地状态保存在 `~/.kickstart/config.json` 和 `~/.kickstart/last-selection.json` 中，因此“工作区预设”最适合沿用当前的本地文件持久化方式，不需要引入额外服务或依赖。

这个功能本身不大，但会同时影响 CLI 首页导航、仓库选择流程、本地数据持久化和预设管理流，因此需要先明确整体交互和数据结构，避免实现时把现有流程搞乱。

## Goals / Non-Goals

**Goals:**
- 支持把一组仓库路径保存为可复用的具名工作区预设。
- 启动时支持在“最近项目”“工作区预设”“管理预设”之间切换。
- 支持用户在最近项目选择完成后，保存为预设并立即打开。
- 支持基础预设管理能力：查看、重命名、删除。
- 尽量复用现有本地缓存目录和 Inquirer 交互风格。

**Non-Goals:**
- 不支持在单个预设内为不同仓库配置不同启动命令。
- 不支持标签、分组、导入导出、云同步。
- 不做复杂的失效路径自动修复，只做打开时的轻量校验。

## Decisions

### 预设数据存储在 `~/.kickstart/workspaces.json`
- 复用当前 `~/.kickstart` 目录，不新增额外配置位置。
- 数据结构采用数组，每项包含 `name`、`repoPaths`、`updatedAt`，便于阅读和后续扩展。
- 备选方案是把预设直接写进 `config.json`，但这会把初始化配置和长期业务数据混在一起，后续维护成本更高，因此不采用。

### 在仓库选择前增加首页模式选择
- 程序启动后先让用户选择进入“最近项目”“工作区预设”还是“管理预设”。
- 这样能保持原有最近项目选择流程基本不变，也能避免把过多操作硬塞进同一个多选界面里。
- 备选方案是在仓库多选界面中混入预设操作入口，但这会让交互理解成本明显升高，因此不采用。

### 预设创建依附于最近项目流程
- 用户在最近项目中勾选完仓库后，再决定是“直接打开”还是“保存为预设后打开”。
- 这样可以最大程度复用现有选择逻辑，也更符合用户心智：先选项目，再决定是否沉淀为预设。
- 备选方案是单独做一个“创建预设”流程，但这会重复仓库选择逻辑，MVP 阶段没必要。

### 打开预设时再校验路径有效性
- 当用户选择某个预设后，再过滤掉本地已不存在的仓库路径；如果全部失效，则直接报错并终止打开。
- 这样可以减少无意义的启动期文件修复逻辑，也能避免程序在用户无感知的情况下偷偷改动预设文件。
- 备选方案是在每次启动时自动清洗无效路径，但这会引入隐式写入和额外 I/O，不适合作为 MVP。

## Risks / Trade-offs

- [预设名称冲突] -> 在创建和重命名时强制校验唯一性，并给出明确提示。
- [预设中的路径失效] -> 打开前过滤无效路径，并提示用户有部分仓库已被跳过。
- [CLI 流程变复杂] -> 首页只保留三个一级入口，最近项目流尽量保持原样。
- [预设文件损坏] -> 沿用现有 JSON 读取容错策略，读取失败时回退为空列表。

## Migration Plan

- 这是一个新增文件能力，不需要对已有用户做迁移。
- 首次保存预设时，如果 `~/.kickstart/workspaces.json` 不存在，则自动创建。
- 原有 `config.json` 和 `last-selection.json` 的行为保持不变。

## Open Questions

- 打开预设时，失效路径是只提示一次还是展示详细列表？MVP 先做简洁提示即可。
- 预设列表按名称排序还是按最近更新时间排序？MVP 建议按最近更新时间倒序，和当前产品的“最近优先”心智保持一致。
